# 反馈迭代与规则进化

## 一、反馈处理流程

### 第一步：接收反馈
用户给出批评或修改建议。

### 第二步：分类失败模式
判断问题属于哪一类：

| 类别 | 特征 | 示例 |
|------|------|------|
| **OOC** | 角色言行不符合设定 | "主角不会说这种话" |
| **剧情乏味** | 缺乏张力、钩子弱、节奏慢 | "看了三页没什么事发生" |
| **逻辑漏洞** | 设定矛盾、情节不合理 | "之前不是说不能飞吗？" |
| **AI味重** | 语言公式化、套路化 | "又是'不是A而是B'" |
| **节奏问题** | 太快或太慢 | "感情线发展得太突然" |
| **情感不够** | 缺乏代入感、共情缺失 | "对这个角色没感觉" |
| **结尾乏力** | 余味不足、收得太草率 | "就这样结束了？" |
| **开篇误导** | 类型承诺错误 | "开篇像喜剧，结果是悲剧" |

### 第三步：定位根因
不只是看「哪里坏了」，还要找「在哪个阶段造成的」：

| 失败模式 | 可能的根因阶段 |
|---------|---------------|
| OOC | Hook 3（角色边界卡未定义或不完善） |
| 剧情乏味 | Hook 4（桥段选择平淡）/ Hook 8（升级不够） |
| 逻辑漏洞 | Hook 2（前文梳理遗漏）/ Hook 3（设定边界不清晰） |
| 公式化表达多 | Hook 13（行文质感校对未严格执行） |
| 结尾乏力 | Hook 8（余味未设计）/ Hook 11（草率收尾） |

### 第四步：针对性修复
- 如果根因在**设定阶段** → 回到Hook 2/Hook 3，补充/修正边界
- 如果根因在**计划阶段** → 回到Hook 10，调整故事计划
- 如果根因在**生成阶段** → 回到Hook 11，重写对应段落

### 第五步：输出修复版本
```markdown
## 修复说明
- **问题分类**：[OOC/剧情乏味/...]
- **根因**：[在哪个阶段出的问题]
- **修复方式**：[具体做了什么调整]

[修复后的正文]
```

## 二、规则进化协议

### 什么应该被固化为规则？

提升条件（满足任意一条即可考虑）：
- 同一类反馈在3个不同故事中重复出现
- 同一个修复方案被成功使用3次以上
- 用户明确要求「以后都这样」
- 修复方案解决了一个「可迁移」的失败模式（不只是当前故事特有的问题）

### 升级路径

| 频率 | 动作 |
|------|------|
| 单次反馈 | 只修复当前故事，不修改规则 |
| 重复2次 | 记录到「待观察」列表 |
| 重复3次+ | 写入对应的reference文件 |
| 影响核心流程 | 更新SKILL.md中的对应钩子 |

### 规则更新的位置映射

| 反馈类型 | 写入哪个reference |
|---------|---------------|
| 某类角色容易OOC | 更新 character-boundary-template.md 的示例 |
| 某类桥段反复无效 | 更新 inspiration-remix-playbook.md 的卡片 |
| 某类公式化表达反复出现 | 更新 prose-polish-rules.md 的禁用列表 |
| 某类钩子反复被用户说不好 | 更新 story-engine-library.md 的钩子库 |
| 某类检查项被漏掉 | 更新 gate-hook-checklist.md |
| 某类质量项反复不通过 | 更新 quality-checklist.md 或 genre-quality-rubric.md |

## 三、版本管理

### 输出版本号
每次生成后，记录版本：
- v1.0 - 初稿
- v1.1 - 根据反馈第一次修复
- v1.2 - 根据反馈第二次修复
- v2.0 - 重大重构（改动超过50%）

### 变更摘要模板
```markdown
## 变更摘要 v1.0 → v1.1
- **触发反馈**：[用户说了什么]
- **失败分类**：[属于哪类问题]
- **修改内容**：[具体改了哪些部分]
- **修改依据**：[参考了哪个规则/边界]
```

### 备份提醒
每次生成后，在对话中提醒用户：

> 💾 当前版本 [v1.0] 已记录，如需回退请告知。
